## 7. 에러 시나리오 및 예외 처리

### 7-1. 서비스 장애 시 Fallback

| 장애 상황 | Fallback 전략 |
|---|---|
| ai-service Down | Redis 캐시에서 유사 추천 결과 조회, 없으면 "일시적으로 추천이 불가" 메시지 + 인기 장소 Top-N 대체 |
| place-service Down | Gateway Circuit Breaker → 캐시된 장소 메타 응답, 없으면 503 |
| seoul-data-service Down | 실시간 혼잡도 데이터는 최종 캐시값 유지 (stale-but-serve) |
| LLM API Timeout | 10초 타임아웃 → 재시도 1회 → 실패 시 Redis 직전 추천 결과 fallback |
| Redis Down | Gateway Rate Limit은 fail-open (요청 허용), JWT Refresh Token은 fail-close (401 반환) |
| Kafka Down | Producer: 로컬 DLQ 저장 → Kafka 복구 시 재발행 / Consumer: 자동 재시도 |

### 7-2. 데이터 정합성 처리

| 상황 | 처리 방식 |
|---|---|
| place-service 장소 삭제 후 북마크 잔존 | 북마크 조회 시 place-service `/internal/places/{placeSeq}/exists` 확인 → 미존재면 `is_deleted` 플래그 응답 |
| recommendation-service 코스에 삭제된 장소 포함 | 코스 조회 시 장소 스냅샷(이름, 이미지) 비정규화 데이터 사용. place 테이블 조회 실패해도 코스 표시 가능 |
| 사용자 탈퇴 후 작성한 리뷰 | 작성자 닉네임을 "탈퇴한 사용자"로 마스킹 표시. 리뷰 본문은 유지 (서비스 신뢰성) |

### 7-3. 보안 취약점 대응

| 취약점 | 대응 |
|---|---|
| JWT 탈취 | Refresh Token Rotation (갱신 시 기존 토큰 무효화) |
| 무차별 대입 공격 | `/api/auth/login` 10req/min IP Rate Limit + 5회 실패 시 5분 lock |
| SQL Injection | JPA/TypeORM Prepared Statement + 입력값 화이트리스트 검증 |
| XSS | 프론트엔드 React Auto-escape + 백엔드 HTML Sanitizer |
| Path Traversal (파일 업로드) | MinIO Object Key는 서버에서 UUID로 생성 (사용자 입력 filename 직접 사용 금지) |
| 민감정보 로그 노출 | 비밀번호·토큰 필드는 Logback MaskingPattern 적용 |
